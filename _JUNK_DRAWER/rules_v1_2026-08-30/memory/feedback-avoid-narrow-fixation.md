Chris has called this out twice now, in two different contexts:
1. Hunch Engine build (2026-08-01, see [[hunch-engine-direction]]): explicitly
   rejected a predefined question taxonomy — "you constantly think too
   narrow."
2. Monetization brainstorm (2026-08-05, see [[monetization-goal-and-paths]]):
   "stop thinking so god damn narrow — so fucking hooked on the banned
   providers... use what I have as reference/foundation." I had anchored on
   the one lens with the biggest proven number (banned-provider matches)
   instead of reasoning from the full wired graph + entity resolution +
   Hunch Engine as the actual asset.

**Why:** Chris built breadth on purpose (31M+ entities, many domains,
open-ended pattern discovery) — collapsing it down to the first easy/proven
example throws away the actual differentiator, whether the task is technical
(Hunch Engine primitive) or strategic (what to sell).
**How to apply:** when brainstorming or designing off "what Ripple has,"
start from the full foundation (the connected graph + resolution engine +
discovery layer) and ask what it enables broadly, before reaching for the
single most-proven narrow example. Related: [[open-brief-means-range]]
(bring 2-3 real options, don't build around one framing).
