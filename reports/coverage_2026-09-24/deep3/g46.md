## 0. The glance's top-value counts can be fake. This is the finding.

**What the glance did:** `battery.py` gets each column's top 5 values with Snowflake's `APPROX_TOP_K`.
That's a sketch. It estimates. It doesn't count.
When nearly every value in a column is unique, it makes up a count. Every value on the list gets the same count.

**Checked: approx vs exact, same column, same query (t1)**

```
column                      glance/approx says           exact max per value
Crossref FUNDER_URI         336 (glance), 346 (rerun)    1
Crossref FUNDER_NAME        346 (rerun)                  4
GDELT GLOBALEVENTID         8                            1
HIFLD OBJECTID              4                            1
ITIS EXPERT                 2 for three names            2, but only for Chris A. Taylor
```

- ITIS: the glance lists Daniela Arenas-Viveros, Matthew E. Neilson and Howard L. Jelks twice each.
  A grouped count (i2) finds exactly one repeated name: Chris A. Taylor (IDs 86 and 134).
- Crossref: the glance got 336 and my rerun got 346. The sketch doesn't even give the same wrong number twice.

**Checked: is it only these tiny tables? No (t2).**
The signature is 3+ top values, all with the same count above 1.
It shows up on **134 columns in 100 of the 552 tables** in `battery.jsonl`. I scanned the file locally, no query.
I tested three suspects outside this group, plus one control:

```
column                           glance says    rows         distinct     real max
SEC DERIV_TRANS_SK               2,102          1,049,121    1,049,121    1
FATCA GIIN                       3,797            516,298      516,298    1
FDA GUDID PRIMARY_DI             4,909          5,083,948    5,061,910    3,539
control: CDC_OVERDOSE STATE      1,596             83,790           54    1,596   (real)
```

- The control is real: 1,596 rows per state is a balanced state-by-month panel.
  **So a flat top isn't always fake.** Each of the 134 needs an exact count before anyone uses it.
- GUDID: the glance's 4,909 is higher than any real count in the column.

**Hit means:** a glance line like "top ID appears N times" on an ID-like column proves nothing.
Any round-1 or round-2 note that read those as duplicates or heavy hitters is unproven.
**Miss would have meant:** exact counts matched the glance, and the "top" lists could be trusted.
**Dull explanation:** that's how the function works. Snowflake documents APPROX_TOP_K as an estimate. Nobody's data is broken.
The fix is on our side: `GROUP BY col ORDER BY COUNT(*) DESC LIMIT 5`, or flag any flat top. Not done. Not my file.

## 1. REFERENCE__INTL_GDELT: dead

GDELT codes world news into events: who did what to whom, and where.

**Checked (g1, g2, q01, q02)**
- 1,015 rows, 1,015 distinct event IDs. No duplicate rows. The glance's "8 each" is the sketch (section 0).
- **Every row has the same added-time: 20260702201500.** GDELT publishes a new file every 15 minutes. This is one of them.
- 204 distinct news URLs. 44 distinct event-country codes.
- 994 events are dated July 2, 2026. 21 have older dates, back to July 2, 2025.
  Sample row: a July 2, 2026 Hawaii Public Radio story, dated 20250702. Likely GDELT reading a date out of the article text.
- **The headers are shifted** (catalog already says so). The real coordinates sit in `EXTRA_COL_16/17` (where it happened), `EXTRA_COL_0/1` and `EXTRA_COL_8/9` (the two actors).
  Sample: `EXTRA_COL_16/17` = 19.2008, -155.443, Kumu, Hawaii.

**Trap:** the catalog suggests "rank by map point." The columns *named* `ACTOR1GEO_LAT`, `ACTOR2GEO_LAT` etc. hold event codes and mention counts.
Sample: `ACTOR1GEO_LAT` = "042", an event code.
The `LIBRARY_MARTS.TIMELINE` copy of this table types those columns as FLOAT. A map built on them would read event code 042 as latitude 42.
Not queried: that's from the TIMELINE column list (q01) plus the sample row.
**Why dead:** 15 minutes of news. No time series, no peer group, no keys. A 15-minute slice can't rank a place against anything.

## 2. REFERENCE__FED_DHS_HIFLD: dead

A slice of the DHS map layer of electric transmission lines.

**Checked (h1, h2, h3)**
- 500 rows, 500 distinct OBJECTIDs. One load, 2026-07-02. The glance's "4 each" is the sketch.
- OBJECTIDs run 305 to 70,273. The full layer is far bigger than these 500.
- **No location at all:** LATITUDE is null on all 500. STATE is empty on all 500. NAME and ADDRESS are blank or NOT AVAILABLE on all 500.
- No voltage column. What's left is owner, status and a source date.
- 17 owners, mostly western: PacifiCorp 133, Tri-State G&T 85, Public Service Co of Colorado 70, Idaho Power 67, WAPA 45.
  **Looks like a slice by owner and region, not a random sample.**
- STATUS: 72 IN SERVICE, 428 NOT AVAILABLE.
  **Status follows who sent the data, not the line.** All 133 PacifiCorp and all 67 Idaho Power lines say NOT AVAILABLE. Midwest Energy is 30 in service, 2 not available.
  2014 source dates: 329 of 359 NOT AVAILABLE.

**Why dead:** the catalog's "who loses most by STATUS" would rank owners by paperwork. With no location, it can't join to anything.
**Next join:** none in this sample. The full layer would need a reload with geometry and voltage.

## 3. REFERENCE__INTL_EUROSTAT: probed

**Checked (e1, e2)**
- 450 rows are two pulls:
  - `TESPN070`, 432 rows: 37 countries and EU groups, 2020-2023, 3 series each (F, M, and a third, likely total).
  - `LFST_DPW_05`, 18 rows: one group code (EU_V_NO), one year (2022). A fragment.
- **INDICATOR is empty on all 450.** The table never says what it measures.
  From Eurostat's site: TESPN070 is the **aggregate replacement ratio for pensions**. That's the median pension of people 65-74 divided by the median pay of people 50-59.
  Source: https://ec.europa.eu/eurostat/databrowser/product/page/TESPN070
- **OBS_STATUS is blank on all 450.** The catalog's "share of each OBS_STATUS" angle is empty.
- UNIT says PC (percent), but values run about 0.3-0.8. Read 0.57 as "pensions are 57% of pay."

**Trap: Turkey, women.**
```
TR women   2020  0.00    2021  14.91    2022  16.46    2023  2.68
TR men     2023  0.69
```
A pension can't be 16 times pay across a whole country. Every other value is under 1.2.
Unknown whether Eurostat sends it this way or our load broke it. Not checked against Eurostat's site. Drop TR women before any chart.

**Checked: peer comparison, women vs men, 2023**
34 countries and EU groups with both numbers (TR left out):
- Women's ratio lower in 22, higher in 11, equal in 1. **Median gap: women 0.02 lower.**
- Widest: **Portugal women 0.50 vs men 0.71. Spain 0.63 vs 0.83.** Then Poland (gap 0.10) and Greece (0.08).
- Other way: Germany women 0.54 vs men 0.46. Denmark, Ireland and Norway women 0.06 higher.

**Hit means:** a real, citable gender pension gap for Portugal and Spain.
**Dull explanation:** this is Eurostat's own published table. Anyone can read it on their site. We add nothing by joining. Not a portfolio lead.
Usable as a small reference for the pension ratio, TR women excepted.

## 4. REFERENCE__XC_CROSSREF_FUNDER_REGISTRY: skip

Crossref's list of research funders and their DOI IDs.

**Checked (x1, x2)**
- 45,661 rows, 45,661 distinct IDs. All start `http://dx.doi.org/10.13039/`. One load, 2026-08-07.
- 45,455 distinct names. Repeated names are different funders:
  4 "Office of the Attorney General" and 4 "Ministry of Higher Education and Scientific Research". Those are different states and countries.
- **Trap: REPLACED_BY_URI holds the letter R on all 347 filled rows.** The pointer to the new ID is cut to one letter.
  So retired IDs can't be mapped to their replacements. It shows in the name repeats: "Shire" has 2 IDs, one marked replaced, and nothing says which ID replaced it.
- **No join in the warehouse.** No other table holds a Crossref funder DOI. bioRxiv has `FUNDER_ROR_ID`, which is a different ID system. Checked in `er.json`, no query.
