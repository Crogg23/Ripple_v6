Why a broken tap still says success

Recon often picks the human landing/help/portal page as the “data URL.” The loader scrapes that HTML, and your two safety gates only catch some of the junk:

The holes: _reject_html only fires on exactly one column (if len(cols) != 1: return), and the density floor is 1% with no minimum-row check. A one-row HTML scrape clears both. — library-onboarding/ingest.py

The 284 “failed” portal taps are expected churn, not a regression

The PORTAL_* entries are a speculative machine crawl: 194 open-data portals fingerprinted, a 338,520-dataset index harvested, each dataset minted as a tap. Nobody vetted that any given resource URL is live or tabular — so they fail exactly how crawled resources fail: 145 dead 404s, 86 HTML-not-data, plus 500s and stub rows. A ~26% junk rate is normal for public portals that constantly rotate resource IDs.

RECOMMENDATION Isolate, don't purge-all or retry-all. Tag every PORTAL_* as provenance = 'speculative_harvest' and exclude the class from your empty-tables / lifecycle dashboards so curated sources stay legible. Then purge the hard 404s + HTML-not-data; leave 500s for a low-priority re-probe.

Three pipeline fixes stop this recurring

  1. 1
    Add a minimum-row floor to the density gate. Any snapshot load under, say, 25 rows is demoted to empty unless the source is known-tiny. Catches every 1–7 row HTML scrape that currently rides in as success.
  2. 2
    Broaden _reject_html. Also fail when a frame is 1–few rows and any cell contains <!DOCTYPE / <html — not just the single-column case.
  3. 3
    Content-type check at recon time. Before codegen, HEAD the chosen URL; if it returns text/html, make recon hunt for the real bulk/API endpoint instead of accepting the landing page. Add a landing-vs-mart row-count drift check to catch stale models like the 8 above.
